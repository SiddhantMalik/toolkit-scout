Behind these APIs is a software layer connecting and optimizing communications networks around the world. With the Twilio APIs, you can build applications that help your users send messages, make phone calls, look up phone numbers, and more. In Twilio s ecosystem, each product corresponds to an API. For example, Twilio Messaging corresponds to the Messaging API. Although each API has its own unique features, they all share a common set of principles and practices. This consistency lets you work with different Twilio APIs in a similar way. You can use the APIs directly over HTTPS or through Twilio SDKs available for several programming languages. This section covers how to work with the Twilio APIs: Make requests to the Twilio APIs , including authenticating your requests, choosing the right content type, and handling webhooks. Work with Twilio API responses , including specifying response formats, paginating results, and handling errors. Handle mutations and conflicts . Follow API best practices . Need some help? We all do sometimes; code is hard. Get help now from our support team , or lean on the wisdom of the crowd by browsing the Twilio tag on Stack Overflow. To verify that you granted the requester permission to your account resources, Twilio requires authentication on every API request. When you create a Twilio account, Twilio generates an Account SID and an Auth Token. The Auth Token provides broad account access and should be protected like a high-privilege password. Supported authentication methods Twilio supports three authentication methods. Choose based on your security requirements and integration needs: OAuth 2.0 — Recommended for new integrations Short-lived access tokens, as brief as one minute Scoped to specific permissions Best for third-party apps and delegated access Requires token refresh mechanism API Keys — Recommended for server-side apps Main API Key: Provides broad account access (avoid for new integrations) Standard API Key: Full account access with SID isolation Restricted API Key: Scoped to specific capabilities (recommended for new integrations) Auth Token authentication — Legacy option Provides broad account access Should only be used when OAuth 2.0 or API keys are not supported Treat as last-resort option Choosing the right authentication method Whenever the integration supports OAuth 2.0 or a Restricted API Key, use it. These options allow you to scope access to the capabilities your integration needs. This limits the potential impact of a leaked credential. Auth Tokens and Main API Keys provide broad account access. Although they remain supported, treat them as legacy or last-resort options rather than the default for new integrations. The following table compares key attributes of each authentication method: Method Scope control Token lifetime Recommended use Security level OAuth 2.0 Highly scoped Short-lived (configurable) Third-party apps, delegated access Highest Restricted API Key Scoped to capabilities Long-lived (until revoked) Server-side apps High Standard API Key Account-level access Long-lived (until revoked) Admin access, account management Medium Auth Token Broad account access Long-lived (until rotated) Legacy integrations only Low OAuth 2.0 and SDK support OAuth 2.0 provides the strongest security posture for API authentication. To simplify implementation, Twilio provides SDK support for OAuth . These SDKs refresh tokens and reduce the amount of code that you must implement for authentication. This reduces the risk of expired token errors. Best practices for all authentication methods Implement the following practices regardless of which authentication method you choose: Prefer short-lived OAuth 2.0 access tokens where appropriate. Rotate client credentials and signing keys according to organizational policy. Revoke credentials immediately when you suspect compromise. Grant each integration only the permissions it needs. Keep authentication logic on the server side and out of browser-delivered code. Never hardcode credentials in source code or client-side apps. Store all credentials in a secrets manager . Even with strong authentication mechanisms available, mistakes in how you store, transmit, or manage credentials undermine all security protections. The following patterns cover common practices that significantly increase risk. These patterns appear frequently in compromised integrations. Avoid these patterns. Practices to avoid Poor authentication practices make credential compromise easy for attackers and incidents expensive to remediate. The following practices increase risk: Keep credentials out of code or repositories Never embed Auth Tokens, Main API Keys, or Restricted API Keys in browser code or mobile apps. Never hardcode credentials in source files including temporary commits you plan to remove. Never hardcode credentials in infrastructure templates, configuration files, or Docker images. Never commit credentials to version control repositories or CI/CD systems. Secure credentials storage Never store credentials in plain-text files on disk. Never store credentials in unencrypted local storage like browsers or mobile devices. Never log full authorization headers, request bodies containing secrets, or environment variables. Never transmit credentials through email, chat systems, screenshots, or issue trackers. Don t reuse or overshare credentials Never share credentials with people, vendors, or support channels. Grant controlled access. Never reuse one credential across multiple unrelated apps or environments. Never reuse credentials after team member changes, vendor relationships end, or deployments change. Never grant access to production credentials to all users. Implement role-based access control. Don t substitute authentication with network controls Never treat a private network connection (VPN, private subnet, firewalls) as a replacement for authentication. Never assume internal only means you don t need to protect credentials. Never substitute network security for app security. Keep authentication mechanisms current Never ignore security advisories for Twilio SDKs, dependencies, frameworks, or infrastructure. Never delay applying security patches to systems that can access Twilio APIs. Never use deprecated or end-of-life versions of authentication libraries. Why these mistakes happen Anti-patterns simplify initial development through the following poor practices: Embedding credentials speeds prototyping. Hardcoding involves less work than integrating a secrets manager. Sharing credentials avoids waiting for access approvals. Skipping secrets management feels like progress until an incident occurs. The development time saved gets lost in incident response, emergency credential rotation, and security audits. Choose needed webhooks Your app can use webhooks with the following Twilio products: Voice Messaging Conversations (classic) Authy Proxy Video Status Facebook Messenger Twilio can also provide information over webhooks: Debugging Usage Alert Your app doesn t require all webhooks. Respond to webhooks With your chosen webhooks, map out how you want to respond to each. Some Twilio webhooks require a response in Twilio Markup Language (TwiML) or JSON. The TwiML you send back to the webhook varies based on what product you are using: TwiML for Programmable Voice TwiML for Programmable Messaging TwiML for Programmable Fax Informational Twilio webhooks require a standard HTTP 200 OK response. This shows that your web app received the webhook. Mock webhook requests for development Once you have identified the webhooks you are planning to use, it s time to write some code! For ad-hoc testing purposes during development, you may find it worthwhile to set up mock HTTP requests to your app. We suggest either using a command-line tool like curl , or a desktop app like Postman . Use the sample webhook requests found in the Twilio documentation as starters for your own requests, or send Twilio webhooks to a service like RequestBin to capture the HTTP request being sent. Create automated tests for webhooks After doing some initial validation of your code, you can write automated tests using your preferred testing framework. Once you deploy your app, you can check the Twilio Debugger for errors when a webhook is sent to your app. Those HTTP requests would make excellent candidates for additional tests for your web app framework. For test-driven development (TDD), you may consider swapping the order of this step and the previous step. Run your app on a public URL Twilio needs to send webhook requests to an internet-reachable URL. Choose from two methods: Deploy your web app code to a development or test server on the public internet. Expose a local environment to the internet using an HTTP tunneling tool like ngrok . (warning) Company network security might not allow tunnels Your network security team might block ngrok or other HTTP tunnels. In those cases, configure a development or testing server that Twilio can reach before deploying your webhook project to a production environment. To learn how to use ngrok to develop webhooks locally, see Webhook testing . Configure your public URL with Twilio Configure your webhook target URL for Twilio requests in the Twilio ecosystem. Twilio Voice might need a webhook URL for inbound voice calls, inbound messages, or inbound faxes. Twilio messaging might need a webhook URL for outbound messages. The typical API request parameter for the webhook URL gets named callback or statusCallback . To send an outbound message, the TwiML Message verb provides an attribute to set the status webhook URL. Validate that webhook requests come from Twilio Once Twilio can send requests to your web app, start validating that Twilio sends your incoming webhooks. To learn more, see Webhooks Security specifically the validating Twilio requests section. If your integration tests use your validation process, Update your integration tests, update the tests. Many test frameworks can set environment variables for test mode as well as production. Keep account credentials outside of your code as a best practice. Test your webhooks with live traffic To test live traffic depends on which webhooks you use, but you can start making phone calls to your Twilio number, sending text messages, or whatever else you have built. Try to exercise as many corner or edge cases as possible with your app. This checks any assumptions you left out of your unit or integration tests. Promote your web app to staging and production Promote your web app to a staging environment, then to production. At each step, update the webhook URL you use with Twilio for the correct environment. Test your webhook with SSL enabled and the certificates you use in production. Twilio webhooks don t work on HTTPS endpoints with self-signed SSL certificates. To learn more, see Webhooks Security . Test credentials that you created in the legacy console before the console migration continue to work. Twilio provides test credentials you can use to exercise parts of the REST API without incurring charges. You use test credentials the same way you use your live credentials, except that you can t sign in to the Twilio CLI with them. When you authenticate with test credentials, Twilio doesn t charge your account, update the state of your account, or connect to real phone numbers . You can therefore simulate buying a phone number or sending an SMS without affecting production data. To protect production data, requests that use test credentials can t interact with resources in your live account. For example, a request made with test credentials can t specify a live account phone number as the From phone number. Find your test credentials To find your test credentials, go to Admin Account management and access the API keys tokens page. Supported resources Test credentials can interact with the following legacy console resources: Buying phone numbers: POST https://api.twilio.com/2010-04-01/Accounts/{TestAccountSid}/IncomingPhoneNumbers Sending SMS messages: POST https://api.twilio.com/2010-04-01/Accounts/{TestAccountSid}/Messages Making calls: POST https://api.twilio.com/2010-04-01/Accounts/{TestAccountSid}/Calls Lookup: GET https://lookups.twilio.com/v2/PhoneNumbers/{PhoneNumber} Requests to any other resource with test credentials return a 403 Forbidden status code. (warning) Warning SMS messages and calls sent by using test credentials don t trigger status callbacks. Learn more about status callbacks for outbound SMS and status callbacks for Voice . Magic input When you make an API request with test credentials, Twilio validates the input exactly as it does for live credentials. In some cases, request validity depends on Twilio s current state. For example, buying a phone number that someone else has already purchased returns an error. To write automated tests that expect specific errors, use magic input values. For instance, the magic phone number +15005550000 , when sent as the PhoneNumber parameter in a POST to IncomingPhoneNumbers , always returns the number unavailable error. Magic inputs depend on the endpoint you re testing and are detailed below. Note : you can t use magic input values with live credentials. Only test credentials work with magic input values. Otherwise, those functions and services will fail with a 403 Forbidden error. Twilio uses the Account SID and Auth Token to authenticate API requests. You can rotate the Auth Token in the Twilio Console or by using this API. Two related endpoints help you manage Auth Tokens: use the Secondary Auth Token endpoint to create or delete a secondary token, and use this endpoint to promote the secondary token. (warning) Rotating Auth Tokens for many subaccounts Each Auth Token change sends email to every owner and administrator of the account. Rotating Auth Tokens across many subaccounts at once can generate a high volume of email, which can delay other messages that Twilio sends to the same recipients, such as Console verification codes. We recommend setting SuppressEmailNotification to true when you rotate Auth Tokens for a large number of accounts, and telling your users about the rotation through your own channels. Defaults to false , so Twilio sends the email. Set to true when rotating Auth Tokens across many subaccounts.
