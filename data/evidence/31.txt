Page Summary outlined_flag The Google Ads API is a programmatic interface for managing Google Ads accounts and campaigns, suitable for large or complex setups. Typical uses of the Google Ads API include automated account management, custom reporting, ad management based on inventory, and Smart Bidding strategy management. The Google Ads API is recommended for developers comfortable with writing code and managing their own software infrastructure. Google Ads scripts, BigQuery Data Transfer service, automated rules, bulk uploads, and Google Ads Editor are alternative tools for automating Google Ads for different needs and technical skill levels. The Google Ads API is the programmatic interface to Google Ads, used for managing large or complex Google Ads accounts and campaigns. You can build software that manages accounts from the customer level down to the keyword level. Typical use cases include: Automated account management : Create and link accounts, manage account hierarchies, and automate user access. Custom reporting : Query performance metrics, segments, and resource attributes using the Google Ads Query Language (GAQL) . Campaign and inventory-based ad management : Create and update Performance Max , Search , Demand Gen , Shopping , Video , and App campaigns, budgets , and assets . Conversion measurement and Smart Bidding strategy management : Upload click, call, and enhanced conversions and configure automated bidding strategies. Is the Google Ads API the right product for me? Google provides multiple products to help automate Google Ads accounts. Use the following table to identify the product that best fits your requirements: Scenario Recommendation I am a developer who wants to build custom software or integrate with the Google Ads API, and I am comfortable managing server and database infrastructure. Use the Google Ads API. Start with the Quickstart to configure access and make your first API call. I am a developer who wants to write custom logic, but I prefer not to manage server infrastructure. Use Google Ads scripts . I am not a developer, but I want to learn basic programming to automate Google Ads. Use Google Ads scripts . I am a data analyst who needs to download Google Ads reports for offline or warehouse analysis. Use the BigQuery Data Transfer Service for Google Ads transfers . I am building Marketing Mix Models (MMM) and need Google Ads data. Use the MMM Data Platform . While many advertisers rely on the Google Ads API for data pulls, the Google Ads API is not ideal for MMM development. I want to manage Google Ads in bulk without writing code. Use automated rules , bulk uploads , or Google Ads Editor . Page Summary outlined_flag A developer token is required to make calls to the Google Ads API and is a 22-character alphanumeric string obtained from the API Center page of your Google Ads manager account. Each developer token has an access level (Test, Basic, or Standard) which determines the number of API calls and the environment (test or production) it can be used in. Generally, a company only needs one developer token, but individual developers and companies creating new tools can apply for a new one if necessary. Both companies and individual developers can apply for a developer token, providing specific details during the application process. Applying for a developer token involves selecting or creating a Google Ads manager account and then completing the API Access form in the API Center. The developer token is a 22-character long alphanumeric string that was used to connect your app to the Google Ads API. Developer tokens were sunset on September 9, 2026 . This guide summarizes the changes and lists the frequently asked questions about this migration to assist the existing developers. Key Point: New to the Google Ads API? You no longer need a developer token or a Google Ads manager account to get started. API access is now managed directly in your Google Cloud project: enabling the API grants Test access (15,000 operations per day on test accounts), and you can apply on the Google Ads API Overview page for Explorer access (automated review and approval in most cases, for up to 2,880 operations per day on production accounts). Follow the Make your first call quickstart or connect an AI assistant with the Google Ads MCP server . Go to Google Ads API Overview in Cloud Console What's changing? We introduced several changes to the Google Ads API onboarding experience and API access management as part of the developer token sunset. This section highlights the key changes. API access levels are associated with Google Cloud projects We sunset developer tokens on September 9, 2026. Your current and active developer token access level was automatically transferred to your Google Cloud projects based on API activity in the 90 days preceding the sunset. You can continue sending developer tokens in your API call headers, but this is optional and ignored by the API servers. Your existing code will continue working without any changes. Your API access levels are determined by the Google Cloud project you used to generate your OAuth credentials. If your app uses the user authentication workflow , then this is the project that owns your OAuth client ID and secret. If you use the service account workflow , then this is the project that owns your service account. A new signup experience for the Google Ads API Note: If you are a developer who needs access to the App Conversion Tracking API , you should continue to sign up for a developer token from the API Center page instead. You can sign up for access to Google Ads API directly in the Google Cloud Console without requiring a Google Ads manager account. Don t sign up for a developer token from the API Center page or attempt to apply for API access from the API Center page in your Google Ads manager account as these processes have been transitioned to Google Cloud Console and won t be processed if initiated from the API Center page. A new API access management experience We have sunset all the new signup and API access management functionality such as applying for API access and managing API access levels in the API Center page in Google Ads manager accounts. These functionalities are available in the Google Ads API Overview page in Google Cloud Console instead. You can still access the API Center page to refer to your historical developer details. This page will completely sunset in the future. New error codes In v25 and later , the Google Ads API throws an AuthorizationError.CLOUD_PROJECT_NOT_APPROVED_FOR_PRODUCTION error if you try to use a Google Cloud project with Test access to make calls to a production account. Older API versions (v24 and earlier) throw an AuthorizationError.ACTION_NOT_PERMITTED error instead. If you run into this error, navigate to the Google Ads API Overview page for your Google Cloud project and apply for Explorer access . Brand verification is required for Basic and Standard access For new Basic and Standard access applications, you must complete brand verification for your Google Cloud project. Existing access holders are not required to complete brand verification, though it is encouraged. Basic access applications are automated and will be reviewed within minutes after brand verification and submission. Because of these process updates, all pending Basic access applications are closed as part of this transition. Affected applicants receive an email with details and should re-apply for Basic access from the Google Ads API Overview page . New API contact emails As we prepare for decommissioning the API Center page , we will transition to using the list of owner and editor users in your Google Cloud project as the sole channel for administrative and mandatory compliance communications. To ensure a smooth transition, we will temporarily continue to send Mandatory Service Announcements (MSAs) to the email address listed in your API Center. We will keep you updated as we finalize the transition of our communication channels. What to do if you are an existing developer Review your Google Cloud project s API access levels: If you are an existing developer, we urge you to review the Google Ads API Overview page of your Google Cloud projects to ensure that they have the same API access level as your existing developer token. Follow the instructions in this guide to address any discrepancies that you may find. Review your API contact email address: Visit the IAM (Identity and Access Management) page for your Google Cloud project. Verify that your active Ads developers and account managers are assigned appropriate owner or editor roles in your Google Cloud project. We will start sending Mandatory Service Announcements (MSAs) to these email addresses to notify you about any future changes to the Google Ads API. We will continue sending MSAs to the contact email address listed in your API Center for a temporary period, and we will inform you whenever this process updates. Fix your app code: We encourage you to update your app to stop sending a developer token as part of your API calls. We have published updated versions of the client libraries , the Google Ads MCP server , and the Google Ads API Developer Assistant that let you make API calls without setting a developer token. We will start rejecting developer tokens in API calls in a future major version of the Google Ads API. If your app uses these libraries, update your app dependencies to use the latest version. Contact the Google Ads API support if you need further assistance or have more questions. Known issues This section documents all the known issues related to the sunset of developer tokens. Users are not given Explorer access or Basic access even after completing Brand verification We are aware of an issue where some users with brand verified projects are rejected when applying for Basic access. The users will receive a rejection email that says Basic Access requires a successfully verified OAuth brand profile. Your application could not be approved because you haven t completed brand verification for your project. Similarly, some users signing up for Explorer access are also rejected with a rejection email that says At this time, we are unable to grant Explorer Access to your Google Cloud project because it does not meet the eligibility criteria required for direct production account access under our Google Ads API Policies and Terms of Service. Root cause Your Google Cloud project may be on Google Cloud Free Trial program or has a suspended or disabled billing account. How to verify Check your Google Cloud billing status . If your billing project shows as Free trial account or is in a suspended or disabled state, you are affected by this issue. Status We have identified the root cause and are working on a fix for this issue. Temporary workaround There are several workarounds to resolve this issue. Select the most suitable option for your use case. Upgrade your Google Cloud project to a paid tier Upgrade your Google Cloud project to a paid tier . Wait for a few minutes and try applying for Basic access again. Remove billing for your Google Cloud project Warning: Removing billing will turn off all other paid Google Cloud services running in that project and may have other undesired effects. Use this workaround only if you plan to use this project exclusively for your Google Ads API integration or if you are comfortable temporarily pausing other cloud services. If you don t have other services running in your Google Cloud project, remove billing for your Google Cloud project . Wait for a few minutes and try applying for Basic access again. Use a different Google Cloud project If you have another Google Cloud project that is brand verified, use that project to apply for Basic access. Projects with newly approved Basic or Explorer access levels receive an AUTHORIZATION_ERROR We are aware of an issue where some users who upgraded their Google Cloud project s access level to approved Basic or Explorer access levels after September 9, 2026 receive an AUTHORIZATION_ERROR when making Google Ads API calls to production accounts. Root cause Google Ads API is not honoring API access level upgrades that were completed from the Google Cloud Console for some projects. How to verify You are affected by this issue if all of the following conditions are true: You have a developer token with Test access level. You used your Google Cloud project and developer token to make Google Ads API API calls prior to September 9, 2026. You upgraded your Google Cloud project s access level to Explorer, Basic or Standard access after September 9, 2026. Your API calls to a production account are failing with an AUTHORIZATION_ERROR . API calls to test accounts are successful. Status We have a fix for this issue and are working on rolling it out to our servers. Once the fix is live, your API calls will start working again. Temporary workaround You can use a new Google Cloud project to apply for Explorer access. Frequently asked questions The following section provides answers to frequently asked questions about the developer token sunset and API access levels. What happens to API access levels? API access levels are still enforced in the Google Ads API. However, these are granted to your Google Cloud Console project instead of your developer token. When you make API calls, your API access levels are determined by the Google Cloud project you used to generate your OAuth credentials. If your app uses the user authentication workflow , then this is the project that owns your OAuth client ID and secret. If you use the service account workflow , then this is the project that owns your service account. How were the projects identified for transferring API access levels? If you already had an approved developer token prior to September 9, 2026, its access levels have been transferred to your Google Cloud projects as follows: We examined the API call logs for the last 90 days to identify which Cloud projects were used to make API calls with your approved developer token. We assigned the developer token s API access levels to all the identified Cloud projects. Can I have multiple Cloud projects with various access levels after this change? Yes, you can have multiple Google Cloud projects with different API access levels. For example, you can have one Google Cloud project with Basic access and another Google Cloud project with Standard access. Example As an example, assume that you have 4 developer tokens and 6 Cloud projects with the following details: Developer Token 1: abcdefghijkl1234567890 has Standard access. It has been used with project IDs: 1234567890 , 5678912345 , 45678912345 . Developer Token 2: xyzabcdefghi6789012345 has Basic access. It has been used with project IDs: 1231235678 . Developer Token 3: asdfgflkjhjz7654321012 has Basic access, but it has never been used to make an API call. It was approved within 90 days prior to September 9, 2026. Developer Token 4: qwertypoiuyu6543298790 had Standard access, but it hasn t been used in the last 90 days. Project ID 9876564900 was used with this developer token more than 90 days ago. Cloud project: Cloud project ID: 7171234567 has never been used with any of the developer tokens to make an API call. The API access levels will transfer from the developer tokens to the Google Cloud projects as follows: Developer token Project ID Access level Explanation abcdefghijkl1234567890 1234567890 Standard access The developer token and project ID are associated with each other. abcdefghijkl1234567890 5678912345 Standard access The developer token and project ID are associated with each other. abcdefghijkl1234567890 45678912345 Standard access The developer token and project ID are associated with each other. xyzabcdefghi6789012345 1231235678 Basic access The developer token and project ID are associated with each other. asdfgflkjhjz7654321012 -- -- The developer token's API access wasn't transferred to any project since it was never used to make an API call. qwertypoiuyu6543298790 9876564900 Test access The developer token's API access was revoked because of inactivity for 90 days. The project's API access level defaults to Test access. -- 7171234567 Test access This is a new project that hasn't been used with any developer token. The project's API access level defaults to Test access. I have more than one approved developer token. Which project will you transfer API access levels? The access levels of each approved developer token are transferred to the Google Cloud projects associated with that developer token. See an example . I use multiple Google Cloud projects. Which project will you transfer API access levels? If you used multiple Google Cloud projects with your approved developer token in the last 90 days, then all those projects will receive the same API access levels as your developer token. See an example . API access levels were assigned to a project I no longer use. How do I fix this issue? If Google Ads API access is assigned to a Google Cloud project you no longer use, no additional action is needed from your side. Google will revoke the API access for the unused project after 90 days of inactivity. API access levels were not assigned to my Google Cloud project. How do I fix this issue? Your Google Cloud project didn t inherit your developer token s access level, likely because you never used your developer token and the Cloud project to make an API call, or your developer token s API access expired because of inactivity. To fix the issue, apply for the appropriate API access level for that project from the Google Ads API Overview page . See an example . Where can I see my project's API access levels? You can see your Google Cloud project s API access level from the Google Ads API Overview page . How do I apply for higher API access levels? You can apply for higher API access levels for your Google Cloud project from the Google Ads API Overview page . What happens to my pending API access application? Any pending Basic access applications that you initiated from your Google Ads manager account s API Center prior to September 9, 2026 will be closed. You should re-apply for Basic access from your Google Cloud project s Google Ads API Overview page . If you are affected by this change, you will receive an email with the necessary instructions. Any pending Standard access applications that you initiated from your Google Ads manager account s API Center as of September 9, 2026 will be reviewed as usual. If approved, the Google Cloud project associated with your developer token will be granted Standard access. Can I re-associate my approved developer token with a new Google Cloud project? Prior to September 9, 2026, the Google Ads API team supported reassociating a developer token with a new Google Cloud project on a case-by-case basis. This is no longer supported as of September 9, 2026, since we have sunset developer tokens. If you need to use a new Google Cloud project, you should apply for the appropriate API access from your Google Cloud project s Google Ads API Overview page . I have an approved developer token, but I never used it. Can I use this developer token? No, you cannot use this developer token. There are two possibilities: Your developer token access might be revoked for inactivity: Under Google policies , Google may revoke your API token if it s not used consecutively for 90 days. If you haven t used your developer token in a while, its access levels were likely revoked because of inactivity. If this is the case, reapply for API access for your Google Cloud project from the Google Ads API Overview page . See an example . Your developer token was approved within 90 days prior to September 9, 2026, but you never used it: Since you never used your approved developer token with a Google Cloud project prior to September 9, 2026, its access levels weren t transferred to the Cloud project. As a result, you cannot use your developer token any longer. We will throw a CLOUD_PROJECT_NOT_APPROVED_FOR_PRODUCTION error if you attempt to make an API call to a production account with this developer token. To fix the error, apply for the appropriate API access from your Google Cloud project s Google Ads API Overview page . See an example . In both these cases, you can apply for Explorer access and Basic access level applications and get them automatically reviewed; you no longer need to work with Google s Compliance team to complete the review process. If you need Standard access, you need a manual review. However, you can share your approved developer token details when applying for Standard access, so that the Compliance team can review your new Standard access application accordingly. Can I stop sending developer tokens as part of my API requests? Yes, you can stop sending developer tokens as part of your API requests. If you use a client library, you may need to upgrade to its latest version. Check the library s change logs to confirm if it supports making API calls without specifying a developer token. I was part of the Cloud managed access level pilot program. How am I affected? The Cloud managed access level pilot program was introduced as a way for Google Cloud developers to make API calls without sending a developer token as part of the API request. Now that we have sunset developer tokens, this program will be discontinued. Your active developer token s access levels have been transferred to your Google Cloud project, so your existing code should continue to work without any changes. If you need to use a new Google Cloud project, you should apply for API access from your Google Cloud project s Google Ads API Overview page . My developer token was part of an allowlist. How am I affected? Google may run pilot programs that give some developers access to experimental features. The access to these features are sometimes provided by adding your developer token to an allowlist. If you were part of such a pilot program, then no action is required from your side. We have updated all the pilot programs to use Google Cloud projects instead of developer tokens as the allowlisting mechanism and transferred the developer token s allowlist status to the associated Google Cloud projects. Your existing code should continue to work without any changes. If you continue facing issues, reach out to your Google Account manager who enrolled you into the pilot program. I have an approved developer token, and I want to use it with a new Google Cloud project. Is that allowed? No, you cannot use a new Google Cloud project with your approved developer token. Since you never used your approved developer token with the new Google Cloud project prior to September 9, 2026, its access levels weren t transferred to the Cloud project. We will throw an CLOUD_PROJECT_NOT_APPROVED_FOR_PRODUCTION error if you attempt to make an API call with this developer token, since developer tokens are no longer used to determine your API access levels. To fix the error, apply for the appropriate API access from your Google Cloud project s Google Ads API Overview page . See an example . My developer token was leaked externally. Do I need to reset my developer token? No, you don t need to reset the developer token in this case. Since we transferred your developer token s API access levels to your Google Cloud project, an unauthorized user can no longer use your developer token with their own Google Cloud project. What happens to the API Center? The existing API Center page within the Google Ads manager account is deprecated and will be removed in the near future. If you already have a developer token, you can still log into your Google Ads manager account and view the details. However, these are provided only for your reference. Don t perform any tasks related to developer token access levels, such as applying for higher API access levels from this page. If you need to apply for higher API access levels, you should do it from your Google Cloud project s Google Ads API Overview page . Do I still need a Google Ads manager account to use the Google Ads API? You no longer need a Google Ads manager account to use the Google Ads API. You need a manager account only if you need to link to and manage multiple accounts using the API. I am a new developer. How do I sign up for Google Ads API? Follow the instructions on the Getting Started guide to sign up for Google Ads API. Don t sign up for a developer token from the API Center of your Google Ads manager account; these applications won t be processed. The API Center will be sunset in the near future. What IAM permissions are required to manage API access levels? You need quota management permissions for your Google Cloud project to manage Google Ads API access levels. The necessary permissions are included by default for the following roles: Owner, Editor, Quota Administrator, and Service Usage Admin. See the quota permissions documentation for more information. You can check the IAM page for your Google Cloud project to see your assigned roles. Work with your Google Cloud project administrator to grant the necessary IAM roles for your Google Cloud project. Page Summary outlined_flag A developer token is required to make API calls to the Google Ads API and its access level controls the number of daily calls and environments. You need a Google Ads manager account to obtain a developer token and a Google Ads client account is the target of your API calls, identified by a 10-digit client customer ID. Making an API call requires obtaining a developer token, configuring a Google Cloud project with a service account and key for authentication, and setting up your Google Ads client account, including granting the service account access. Depending on your preference for making API calls, you can either download a client library or use HTTP clients like curl or the Google Cloud CLI. To make an API call using a client library or curl, you will need to provide your developer token, client customer ID, and the JSON key file path for your service account credentials in the configuration. This quick start guide helps you make your first API call to the Google Ads API. Key concepts Google Cloud project: A Google Cloud project forms the basis for creating, enabling, and using all the Google services, including managing APIs and OAuth 2.0 API credentials. You can create one from the Google Cloud Console . API access level: The API access level of your Google Cloud project controls the number of API calls you can make per day and the environments to which you can make API calls. Your project s API access level is listed on your project s Google Ads API Overview page . Google Ads manager account: A Google Ads manager account is used to manage other Google Ads accounts, which could be a collection of Google Ads client accounts or other Google Ads manager accounts. Google Ads client account: The Google Ads account used for running ads that you want to target with API calls. Client customer ID: The 10-digit number that identifies a Google Ads client account. If you copied this ID from the Google Ads UI, make sure to remove the hyphens. OAuth 2.0: OAuth 2.0 is an industry-standard protocol for authorization, used by all Google APIs. You need a service account and key to generate OAuth 2.0 credentials to make API calls. Service account: A special type of Google Account that belongs to your application rather than to an individual user. It is used to authenticate your application to the Google Ads API. You need a Google Cloud project to obtain a service account. Service account key: A JSON app credential file that contains the private key for your service account. It is used to generate OAuth 2.0 credentials to authenticate a service account when making an Google Ads API API call. You need a service account to obtain a service account key. Prerequisites To make a Google Ads API call, you should complete the following steps. Configure your Cloud project for Google Ads API access The Google Cloud project is used for managing Google APIs and OAuth 2.0 API credentials. You can find your existing Google Cloud projects or create one by visiting the Google Cloud console . Start by enabling the Google Ads API in your project: Enable Google Ads API Next, visit the Google Ads API Overview page . The page displays your current API access level. If your current API access level is Test , then expand the Upgrade access level section. Follow the instructions to apply for Explorer access level. Once you complete your application, Google will automatically review your application and upgrade it to Explorer in most cases. If you weren t granted Explorer access, don t worry; this guide will provide the appropriate instructions when configuring your Google Ads client account . Create a service account Key Point: Note both the service account email address and the service account key you generate in this step. You will need them when making the API calls. You need a service account and service account key to make API calls. If you are already using another Google API and have created an OAuth 2.0 service account and key, you can skip this step and reuse the existing credentials. How to create a service account and key In the Google Cloud console, go to Menu menu IAM Admin Service Accounts . Go to Service Accounts Select your service account. Click Keys Add key Create new key . Select JSON , then click Create . Your new public/private key pair is generated and downloaded to your machine as a new file. Save the downloaded JSON file as credentials.json in your working directory. This file is the only copy of this key. Don't commit credentials.json to version control (for example, add it to your .gitignore file). Click Close . Configure your Google Ads client account Key Point: Make a note of the 10-digit Google Ads client customer ID, without the hyphens. You ll need this ID to specify which account you re making API calls against. Start by identifying the Google Ads account you re making API calls against. The type of account you can make API calls to depends on the API access level of your Google Cloud project. Check your Google Ads API overview page to find out your API access level. Explorer, Basic Standard access levels You can make calls to your Google Ads production account. However, you can create a Google Ads test account by following the instructions on the Test access tab if required. Test access Your Google Cloud project cannot be used to make API calls to a Google Ads production account. You can make API calls against Google Ads test accounts only. How to create a Google Ads test account The following instructions create a Google Ads test manager account and a Google Ads test client account underneath it. Click Create a test manager account to open the Google Ads account selection page. If prompted, sign in with a Google Account that isn't linked to your Google Ads production manager account, or click Create account to create a new Google Account. Create a test manager account On the account selection page, click New Google Ads Account (or click Create a new account if the Finish setting up your account? dialog appears). The account selection page does not display a test indicator, but opening it from Create a test manager account configures the signup flow to create a test manager account. On the Confirm your business information page, enter an Account display name , select a Primary use of the account option, select your country, time zone, and currency. Confirm the red Test account label in the upper-right corner, click Submit , and then click Explore your account to open your test manager dashboard. While in your Google Ads test manager account, create a Google Ads test client account: Click Accounts add_circle Create new account . Enter an account name, select your country, time zone, and currency, and save the account. Any client accounts you create from your test manager account are automatically test accounts. (For verification guidance, see View test accounts ). Optional: Create at least one test campaign under the test client account from the Google Ads page. If you skip campaign creation, your first API call in Make an API call succeeds but returns an empty response (zero campaigns). To make an API call to a Google Ads customer, you must grant access and appropriate permissions to your service account to the Google Ads customer account. To do this, you need administrator access to the customer account. How to grant the service account access to your Google Ads account Start by signing in to your Google Ads account as an administrator. Navigate to Admin Access and security . Click the add_circle button under the Users tab. Type the service account email address into the Email input box. Select the appropriate account access level and click the Add account button. Note that Email access level is not supported for service accounts. The service account is granted access. [Optional] You cannot grant administrator access to a service account during initial setup. If your API calls require administrator access, you can upgrade the access as follows. Click the drop-down arrow next to the access level of the service account in the Access level column. The Model Context Protocol (MCP) is an open standard that lets large language models (LLMs) securely interact with external data and applications. The Google Ads MCP server provides a standardized bridge to the Google Ads API. It lets AI agents retrieve and analyze account data, create assets, upload videos, and manage labels by using natural language. Community resources and support GitHub repository: Find demos and examples, report bugs, or suggest features in the google-ads-mcp repository . Use the Issues tab for bug reports and feature requests. Community: Join the #ads-api-ai-tools channel on the Google Advertising Community Discord . Technical overview Integrating the Google Ads MCP server removes the need to write custom code for Google Ads API authentication, resource fetching, data parsing, and supported asset or label mutations. The server exposes callable tools and reference resources (see Core capabilities ) that an LLM can inspect and invoke. Key specifications Protocol: MCP (Model Context Protocol) Mode: Read and partial mutate (asset creation, video uploads, and label management with propose-and-confirm validation , or configurable read-only mode ) Language: Python 3.10 or later Transport: Standard input/output ( stdio ) or Streamable HTTP ( streamable-http on Cloud Run) Authentication: Application Default Credentials (OAuth 2.0 user credentials or service account) for local stdio , or OAuth 2.0 Web application credentials for remote HTTP Telemetry: Appends google-ads-mcp/VERSION to the x-goog-api-client gRPC request header for usage statistics How the interaction loop works Request: You submit a prompt such as How is my campaign performance this week? or Create a callout asset for our summer sale . Discovery: The LLM inspects its available tools and resources and selects a matching google-ads-mcp tool. Execution or dry-run validation: Read tools query the Google Ads API directly. Mutate tools first run in propose mode ( validate_only=True ) to validate inputs without committing changes (see Propose-and-confirm safety workflow ). Context injection: The MCP server returns structured query results, or proposed change_items entries and a verification checksum digest, to the LLM s context window. Response and confirmation: The LLM presents an answer or asks you to confirm the proposed changes. After you approve, the LLM calls the mutate tool again with validate_only=False and the matching checksum value to commit the change. Get started Follow these steps to configure and run the Google Ads MCP server locally. To deploy a shared remote service instead, see Deployment on Google Cloud . Prerequisites Before you configure the server, complete the following prerequisites in your local environment and the Google Cloud console : Google Cloud project: Create or select a Google Cloud project with the Google Ads API enabled. Enabling the API grants Test access for testing read and mutate workflows against test accounts . To access production accounts, check the Google Ads API overview page for Explorer, Basic, or Standard access, or apply for one of these access levels . Otherwise, production calls fail with an AuthorizationError.CLOUD_PROJECT_NOT_APPROVED_FOR_PRODUCTION error. Google sunset developer tokens ( GOOGLE_ADS_DEVELOPER_TOKEN ) on September 9, 2026. The Google Cloud project that owns your OAuth client or service account determines your API access level. Credentials: Local stdio mode authenticates with Application Default Credentials (ADC) from an OAuth 2.0 client secret JSON file or a service account in your Cloud project. Set the GOOGLE_CLOUD_PROJECT environment variable when needed to specify your default quota or ADC project. Remote streamable-http deployments instead require an OAuth 2.0 Web application Client ID and Client secret (see Deploy to Google Cloud Run ). Local software (for stdio mode): Install Python 3.10 or later , pipx , and the gcloud command-line tool (used to generate user ADC files). Configuration Generate Application Default Credentials (ADC) using an OAuth client from your API-enabled Google Cloud project and include the Google Ads API scope: gcloud auth application-default login \ --scopes = https://www.googleapis.com/auth/adwords,https://www.googleapis.com/auth/cloud-platform \ --client-id-file = PATH_TO_CLIENT_SECRET_JSON Replace the following: PATH_TO_CLIENT_SECRET_JSON : the path to your OAuth 2.0 client secret JSON file. This command prints Credentials saved to file: [PATH_TO_CREDENTIALS_JSON] (such as ~/.config/gcloud/application_default_credentials.json on Linux and macOS). To authenticate with a service account instead, skip this step and point GOOGLE_APPLICATION_CREDENTIALS to your service account key JSON file, or pass --impersonate-service-account to gcloud auth application-default login . Add the server to your host s MCP configuration file (such as ~/.gemini/config/mcp_config.json , ~/.gemini/settings.json , or ~/.claude/settings.json ): { "mcpServers" : { "google-ads-mcp" : { "command" : "pipx" , "args" : [ "run" , "--spec" , "google-ads-mcp==0.0.6" , "google-ads-mcp" ], "env" : { "GOOGLE_CLOUD_PROJECT" : "PROJECT_ID" , "GOOGLE_APPLICATION_CREDENTIALS" : "PATH_TO_CREDENTIALS_JSON" } } } } Replace the following: PROJECT_ID : your Google Cloud project ID. PATH_TO_CREDENTIALS_JSON : the path to the ADC JSON file printed in step 1, or to your service account key JSON file. You can omit GOOGLE_APPLICATION_CREDENTIALS when using the default gcloud ADC file location. To access client accounts through a manager account, set GOOGLE_ADS_LOGIN_CUSTOMER_ID (10 digits, without hyphens) in env , or pass the login_customer_id parameter on individual tool calls. Tip: For faster startup, install the package once with pipx install google-ads-mcp and set command : google-ads-mcp (with args : [] ). When a new Google Ads API version such as v26.2 is released, run pipx upgrade google-ads-mcp (or pipx run --no-cache ) to update the bundled google-ads Python client library to 35.x+ . These tools also generate client library code, such as scripts to link created assets to campaigns or perform other unsupported mutations: Google Ads API AI agent skills: Portable workflow modules (including google-ads-api-mcp-setup , google-ads-api-account-diagnostics , and google-ads-api-quickstart ) that help your agent use the Google Ads MCP server with lower token overhead. Run the following command to install them (requires Node.js ), or see the Google Ads API AI agent skills guide for Antigravity, Claude Code, Codex, and Cursor setup: npx skills add google/skills/skills/ads Google Ads API Developer Assistant: An open-source plugin (not an officially supported Google product) for Google Antigravity and Claude Code that provides local Protobuf schema inspection, GAQL validation, client library code generation, and offline conversion troubleshooting. See Choose the right Google Ads AI tool or follow the installation guide . Core capabilities The following sections describe the server s read tools, partial mutate tools, and reference resources. Starting in v0.0.6 , tools register by default with their category namespace prefix (such as search_search ). When upgrading prompts or allowlists from unprefixed releases, update tool names or set an empty prefix ( ) in tools_config.yaml (see Configure tool namespaces and read-only mode ). Read tools customers_list_accessible_customers (tool list_accessible_customers ): Returns the Google Ads customer IDs directly accessible to the authenticated user. search_search (tool search ): Builds and runs GAQL SearchStream queries from structured parameters ( customer_id , resource , and fields , plus optional conditions , orderings , limit , and login_customer_id ) rather than a raw GAQL string. Every query appends PARAMETERS omit_unselected_resource_names=true to fetch resource attributes, metrics, segments, budgets, and status cleanly. metadata_get_resource_metadata (tool get_resource_metadata ): Retrieves selectable, filterable, and sortable attributes, metrics, and segments for a Google Ads API resource type (for example, campaign ). Use this metadata to discover valid query fields—including metrics and segments added in minor releases such as v26.2—before calling the search_search tool. Mutate tools (partial support) assets_create_asset (tool create_asset ): Creates standalone Google Ads assets with dedicated parameters for TEXT , IMAGE , YOUTUBE_VIDEO , SITELINK , CALLOUT , and STRUCTURED_SNIPPET asset types. Pass the extra_params dictionary for other mutable AssetService types (such as PRICE , PROMOTION , CALL , or BUSINESS_MESSAGE ), and include root-level final_urls alongside sitelink_link_text for SITELINK assets. Local file paths ( image_asset_path ) work in local stdio mode only. For remote HTTP deployments, pass the base64-encoded image_asset_data parameter with image_asset_mime_type set to IMAGE_PNG , IMAGE_JPEG , or IMAGE_GIF (up to 20 MB). assets_upload_video_asset (tool upload_video_asset ): Uploads a local video file ( .3gp , .avi , .flv , .mkv , .mov , .mp4 , .mpeg , .mpg , .ogg , .webm , or .wmv ) to YouTube through the Google Ads API as a FastMCP background task in local stdio mode only. Both video_title and video_description are required parameters. The video_privacy parameter accepts UNLISTED (default) or PUBLIC (allowed only on advertiser-owned brand channels with user OAuth). This tool returns a Google Ads video_upload_id value (and resource name), not the 11-character YouTube video_id . Query you_tube_video_upload with the search_search tool (filtering by you_tube_video_upload.video_upload_id ) until you_tube_video_upload.state = PROCESSED . Then pass you_tube_video_upload.video_id as the youtube_video_id parameter to assets_create_asset ( asset_type= YOUTUBE_VIDEO ). labels_manage_labels (tool manage_labels ): Creates, updates, and removes account labels, including name, description, and hex background color. labels_manage_label_associations (tool manage_label_associations ): Supports CREATE and REMOVE label association operations ( UPDATE is not supported) on CAMPAIGN , CUSTOMER , AD_GROUP , and AD_GROUP_CRITERION resources. For CUSTOMER resources, resource_id is optional and defaults to customer_id . Pass a composite {ad_group_id}~{criterion_id} ID for AD_GROUP_CRITERION resources, and remove associations by passing either resource_id and label_id or association_resource_name . Ad-level AD_GROUP_AD labels are not supported. Note: Mutate support covers standalone asset creation, video uploads, and label management only. The server cannot link assets to campaigns, ad groups, or asset groups, or configure ad-level asset automation settings (such as OVERLAY_TEXT_ON_VIDEOS in v26.2). It also cannot create, modify, pause, or enable campaigns, ad groups, ads, budgets, or bids. For unsupported mutations, pair the server with companion code-generation tools (see Equip your agent with skills and the Developer Assistant ). Reference resources The server exposes four read-only MCP resources that remain mounted regardless of your tools_config.yaml settings: resource://discovery-document : JSON REST discovery overview of Google Ads API resources, service methods, and schemas. It complements the metadata_get_resource_metadata tool, which returns selectable, filterable, and sortable GAQL query fields. resource://metrics : HTML reference documentation for Google Ads API metrics. resource://segments : HTML reference documentation for Google Ads API segments. resource://release-notes : HTML Google Ads API release notes covering version changes and new features. Propose-and-confirm safety workflow Every mutate tool ( assets_create_asset , assets_upload_video_asset , labels_manage_labels , and labels_manage_label_associations ) enforces a two-step propose-and-confirm workflow to help prevent unintended account modifications: Propose ( validate_only=True , default): Validates inputs without committing changes. The asset and label tools execute a live Google Ads API validate_only dry run. Because YouTubeVideoUploadService has no dry-run mode, assets_upload_video_asset instead validates the local file and binds its size and modification timestamp. Each tool returns human-readable change_items entries and a stateless SHA-256 checksum digest bound to the customer_id parameter and request payload. Confirm ( validate_only=False ): After presenting the change_items list and receiving your approval, the agent calls the tool again with validate_only=False , the identical customer_id parameter and arguments, and the checksum value from step 1. The server rejects any missing or mismatched checksum before mutating the account. Note: The checksum value is an unkeyed SHA-256 digest of the request parameters that works statelessly across Cloud Run instances. It prevents accidental parameter drift or local file swaps across turns, but does not replace access control. To hard-block mutations, disable the labels and assets namespaces in tools_config.yaml . Configure tool namespaces and read-only mode The server bundles a default tools_config.yaml file with all five tool categories ( customers , search , metadata , labels , and assets ) enabled. Customize tools_config.yaml to selectively enable or disable individual tools or namespaces, change or remove namespace prefixes, or enforce a strictly read-only deployment. Important: Whenever namespaces is non-empty, any omitted category is disabled by default , whereas an empty namespaces: {} mapping enables all five categories. Include every category that you want to keep enabled—a file containing only labels: false and assets: false disables the read tools too. At startup, the server resolves tools_config.yaml in the following order: An explicit path in the GOOGLE_ADS_MCP_TOOLS_CONFIG environment variable (recommended for local stdio hosts, whose working directory can differ from your project folder). A tools_config.yaml file in the server s current working directory. The default tools_config.yaml file bundled with the package. If GOOGLE_ADS_MCP_TOOLS_CONFIG points to a missing file, or if any resolved configuration file is invalid, the server raises an error at startup instead of falling back to defaults. The following minimal tools_config.yaml file enforces a strictly read-only deployment: namespaces : customers : true search : true metadata : true labels : false assets : false The following tools_config.yaml file customizes prefixes and filters individual tools (for example, exposing the base64 create_asset tool on Cloud Run while disabling the local-only upload_video_asset tool): namespaces : # Default prefix ("customers_list_accessible_customers") customers : true # Empty prefix mounts unprefixed tool names ("search") search : "" # Custom prefix ("schema_get_resource_metadata") metadata : "schema" # Enable only specific tools in a multi-tool category assets : enabled_tools : - create_asset Sample prompts to start Try the following prompts in your MCP client after connecting the server. Ask what the server can do What can the google-ads-mcp server do? Ask about customers What customers do I have access to? Ask about campaigns How many active campaigns do I have? How is my campaign performance this week? Give me a report of the top spending campaigns split by device category over the last 7 days for account 1234567890 Create assets, upload videos, and manage labels Create a callout asset with the text Free Shipping for account 1234567890 Upload /path/to/promo.mp4 with title Summer Sale and description Summer promo video for account 1234567890 Create a label named Q4 Promo with background color #34A853 and apply it to campaign 9876543210 in account 1234567890 Note: Video uploads require local stdio mode. Creating a new label and applying it to a campaign runs two sequential propose-and-confirm cycles so the new label_id value can be validated in the association request. Deployment on Google Cloud To share the MCP server across multiple agents or run it as a web service, host it on Google Cloud Run or another cloud infrastructure provider instead of running it locally. Prerequisites A Google Cloud project with the Google Ads API enabled (see Prerequisites for production access requirements). The gcloud command-line tool installed, authenticated, and configured with an active project: gcloud config set project PROJECT_ID Replace the following: PROJECT_ID : your Google Cloud project ID. Build and push a Docker image Use Cloud Build to build and push the container image to Artifact Registry without installing Docker locally: Create a repository in Artifact Registry: gcloud artifacts repositories create mcp-servers \ --repository-format = docker --location = us-central1 Build and submit the image from a release tag in the GitHub repository (or from . in a local checkout if you customized Dockerfile or tools_config.yaml ): gcloud builds submit https://github.com/googleads/google-ads-mcp \ --git-source-revision = v0.0.6 \ --tag = us-central1-docker.pkg.dev/PROJECT_ID/mcp-servers/google-ads-mcp:v0.0.6 Replace the following: PROJECT_ID : your Google Cloud project ID. Rebuild and redeploy the image whenever you update google-ads-mcp or upgrade the bundled google-ads Python client library for new Google Ads API releases (such as v26.2). Deploy to Google Cloud Run Configure the following environment variables and secrets for your Cloud Run service: GOOGLE_ADS_MCP_OAUTH_CLIENT_ID : The OAuth 2.0 Web application Client ID from your API-enabled Google Cloud project for application-level OAuth authentication. Complete the following OAuth configuration steps: Add the authorized redirect URIs for any AI clients that you plan to connect (such as https://claude.ai/api/mcp/auth_callback , https://chatgpt.com/connector_platform_oauth_redirect , or https://antigravity.google/oauth-callback ). Add the https://www.googleapis.com/auth/adwords scope to the OAuth consent screen under APIs Services OAuth consent screen Data Access ( Add or remove scopes ). If your OAuth consent screen publishing status is set to Testing (the default), add the Google Accounts connecting to the MCP server as Test users under APIs Services OAuth consent screen Audience ( Test users + Add users ). GOOGLE_ADS_MCP_OAUTH_CLIENT_SECRET : The OAuth Client secret corresponding to your OAuth Client ID. GOOGLE_ADS_MCP_BASE_URL : The public base URL of your MCP server (for example, https://google-ads-mcp-xyz-uc.a.run.app ). Cloud Run assigns this URL during initial deployment, so deploy without this variable first and update the service afterward. GOOGLE_ADS_MCP_JWT_SIGNING_KEY (recommended for multi-instance Cloud Run) : A persistent secret that signs FastMCP JWTs across container restarts and horizontal scaling. GOOGLE_ADS_MCP_STORAGE_TYPE (recommended for multi-instance Cloud Run) : Backend for OAuth client registrations and tokens. Supported values are redis , firestore , filetree (with GOOGLE_ADS_MCP_STORAGE_PATH for non-Cloud Run VM or mounted-volume deployments), and memory . Setting a backend-specific variable selects that backend even if GOOGLE_ADS_MCP_STORAGE_TYPE is unset. When all GOOGLE_ADS_MCP_STORAGE_* backend variables are unset, FastMCP uses its default container-local storage; for single-instance testing with local or memory storage, pass --max-instances=1 : redis : Set GOOGLE_ADS_MCP_STORAGE_REDIS_URL (defaults to redis://localhost:6379/0 ) and install py-key-value-aio[redis] in a custom Dockerfile . Redis expires entries automatically. firestore : Optionally set GOOGLE_ADS_MCP_STORAGE_FIRESTORE_PROJECT (defaults to the ADC project) and GOOGLE_ADS_MCP_STORAGE_FIRESTORE_DATABASE (defaults to (default) ). Install .[firestore] in a custom Dockerfile , provision a Firestore database, and grant the roles/datastore.user Identity and Access Management (IAM) role to the Cloud Run service account. The Firestore store filters expired entries on read without deleting them. Because it stores expires_at as a string, Firestore time to live (TTL) policies can t delete expired entries. For long-running deployments, plan periodic cleanup or use Redis. memory : Ephemeral in-memory storage (useful only with --max-instances=1 ). GOOGLE_ADS_MCP_STORAGE_ENCRYPTION_KEY (optional) : Dedicated Fernet encryption key (or high-entropy secret) for stored OAuth state. This setting and GOOGLE_ADS_MCP_STORAGE_DISABLE_ENCRYPTION=true apply only when an explicit GOOGLE_ADS_MCP_STORAGE_* backend is configured. If omitted, the server derives an encryption key from GOOGLE_ADS_MCP_JWT_SIGNING_KEY , or falls back to GOOGLE_ADS_MCP_OAUTH_CLIENT_SECRET when no JWT signing key is set. Setting a dedicated encryption key prevents rotating that fallback secret from invalidating stored OAuth tokens. PORT (optional) : Listening port in streamable-http mode (defaults to 8080 ; Cloud Run sets this automatically). GOOGLE_ADS_LOGIN_CUSTOMER_ID (optional) : Default 10-digit manager customer ID (without hyphens) used when tool calls omit the login_customer_id parameter. GOOGLE_ADS_MCP_TOOLS_CONFIG (optional) : Container path to a custom tools_config.yaml file (for example, mounted from Secret Manager at /etc/mcp/tools_config.yaml to enforce read-only mode without rebuilding the image). See Configure tool namespaces and read-only mode . Store GOOGLE_ADS_MCP_OAUTH_CLIENT_SECRET and GOOGLE_ADS_MCP_JWT_SIGNING_KEY in Secret Manager and deploy the service to Google Cloud Run: gcloud run deploy google-ads-mcp \ --image = us-central1-docker.pkg.dev/PROJECT_ID/mcp-servers/google-ads-mcp:v0.0.6 \ --platform = managed \ --region = us-central1 \ --allow-unauthenticated \ --set-env-vars = "GOOGLE_ADS_MCP_OAUTH_CLIENT_ID=CLIENT_ID" \ --set-secrets = "GOOGLE_ADS_MCP_OAUTH_CLIENT_SECRET=MCP_OAUTH_CLIENT_SECRET:latest,GOOGLE_ADS_MCP_JWT_SIGNING_KEY=MCP_JWT_SIGNING_KEY:latest" After Cloud Run completes the deployment, retrieve the assigned service URL and update the service with the GOOGLE_ADS_MCP_BASE_URL environment variable: gcloud run services update google-ads-mcp \ --region = us-central1 \ --update-env-vars = "GOOGLE_ADS_MCP_BASE_URL=https://CLOUD_RUN_SERVICE_URL" Replace the following: PROJECT_ID : your Google Cloud project ID. CLIENT_ID : your OAuth 2.0 Web application Client ID. MCP_OAUTH_CLIENT_SECRET : the Secret Manager secret name storing your OAuth 2.0 Client secret. MCP_JWT_SIGNING_KEY : the Secret Manager secret name storing your JWT signing key. CLOUD_RUN_SERVICE_URL : the hostname assigned to your Cloud Run service (for example, google-ads-mcp-xyz-uc.a.run.app ). Authentication and security model Deploying with --allow-unauthenticated disables Cloud Run s infrastructure IAM check ( roles/run.invoker ) so external AI clients can connect without Google Cloud service account tokens. Authentication is delegated to the application layer instead: When GOOGLE_ADS_MCP_OAUTH_CLIENT_ID and GOOGLE_ADS_MCP_OAUTH_CLIENT_SECRET are set, the server enforces Google OAuth 2.0 on every request and returns a 401 Unauthorized HTTP status code to unauthenticated callers. Every tool call executes under the authenticated caller s OAuth identity. Omitting --allow-unauthenticated requires callers to pass Google Cloud OIDC identity tokens with every request. Standard AI clients (such as Claude and ChatGPT) use end-user OAuth rather than Google Cloud IAM tokens, so direct connections require --allow-unauthenticated paired with application-level OAuth. Caution: Never omit GOOGLE_ADS_MCP_OAUTH_CLIENT_ID and GOOGLE_ADS_MCP_OAUTH_CLIENT_SECRET when deploying with --allow-unauthenticated . Those environment variables switch the server from local stdio mode to streamable-http transport. Without them, the server falls back to Application Default Credentials (ADC) and exposes the container s service account credentials to unauthenticated callers. Configure the MCP client After deployment, configure your MCP client with the Cloud Run service URL. Because the server enforces OAuth 2.0, your client must support the MCP OAuth flow or supply an authorized Bearer token: OAuth-enabled clients: In clients that support MCP OAuth discovery (such as Antigravity), connecting triggers a Google sign-in prompt to grant the https://www.googleapis.com/auth/adwords scope (shown as .../auth/adwords in the Google Cloud console). Third-party AI platforms (Claude, ChatGPT): In your client s connector settings, add a custom connector pointing to your service URL with the /mcp path (for example, https://google-ads-mcp-xyz-uc.a.run.app/mcp ). Select OAuth 2.0 authentication with your OAuth Client ID and Client secret, and confirm that the client s callback URI is in your OAuth client s authorized redirect URIs. Clients without OAuth support: Clients that don t support HTTP OAuth flows receive a 401 Unauthorized HTTP status code. For those clients, use the local stdio configuration instead. The following example configures the gemini command-line tool in ~/.gemini/settings.json (for Google Antigravity in ~/.gemini/config/mcp_config.json , replace httpUrl with serverUrl or url ): { "mcpServers" : { "google-ads-mcp" : { "httpUrl" : "https://CLOUD_RUN_SERVICE_URL/mcp" } } } Replace the following: CLOUD_RUN_SERVICE_URL : the hostname assigned to your Cloud Run service (for example, google-ads-mcp-xyz-uc.a.run.app ). Page Summary outlined_flag Google Ads API utilizes the OAuth 2.0 protocol for authentication and authorization, allowing your app to access user accounts without handling login information. In addition to OAuth 2.0 credentials, a developer token is also required to make Google Ads API calls. While all Google-supported OAuth 2.0 scenarios work, this guide focuses on the most common ones for Google Ads API developers. The recommended OAuth 2.0 approach depends on your specific application scenario, such as integrating with existing Google APIs, managing your own accounts, or managing accounts on behalf of other users. Note: You should configure your OAuth credentials using the same Google Cloud project where you have enabled the Google Ads API and requested an appropriate API access level for the Google Ads API to work correctly. Just like other Google APIs, Google Ads API uses the OAuth 2.0 protocol for authentication and authorization. OAuth 2.0 enables your Google Ads API client app to access a user s Google Ads account without having to handle or store the user s login info. Broadly speaking, all the OAuth 2.0 authorization scenarios that Google supports also work with Google Ads API. However, this guide focuses on the scenarios that are most common for Google Ads API developers. Scenario Recommended approach My app already uses one or more Google APIs. I have already built support for OAuth 2.0 workflows for my app, and just need to add Google Ads API functionality to my existing app. Make sure your authorized user or your service account has access to the Google Ads accounts you are making API calls to. For more information, see the Google Ads access model . See the multi-user authentication workflow or the service account workflow depending on the approach you are using with the rest of the Google APIs that your app is using. I am building an app that manages Google Ads accounts that I already have access to. If I need to manage new Google Ads accounts in the future, I will gain access to those accounts by linking them under my Google Ads manager account. OR Someone will invite me to manage those accounts. Use the service account workflow . If your organizational policies or account setup prevent you from using service accounts, use the single-user authentication workflow instead. I am building an app that manages Google Ads accounts on behalf of other users. My app will build a user screen that lets the signed-in users connect to their Google Ads accounts and authorize my app to manage those accounts on their behalf. Use multi-user authentication . To review and revoke access for third-party applications connected to your Google Account, visit your Google Account permissions page . Page Summary outlined_flag Google Ads API developer tokens have an access level determining production account access and operation limits, and permissible use defining allowed API features. There are three access levels: Test Account Access for test accounts with a 15,000 operation limit, Basic Access for test and production accounts with a 15,000 operation limit, and Standard Access for test and production accounts with an unlimited operation limit. You start with Test Account Access and can apply to increase your access level through additional steps. Permissible use, applicable to Basic and Standard Access, is based on intended API use and determines specific feature access like ad creation/management, reporting, or keyword research. Your Google Cloud project is assigned an access level and permissible use. The access level determines whether you can affect production accounts and the number of operations and requests that you can execute daily. Permissible use determines the specific Google Ads API features that the project is allowed to use. Key Point: Getting started with the Google Ads API? Developer tokens were sunset on September 9, 2026 , and API access levels are now managed per Google Cloud project. After you enable the Google Ads API (which grants Test access), you can immediately apply on the Google Ads API Overview page in the Google Cloud Console for Explorer access (automated review and approval in most cases, for up to 2,880 operations per day against production accounts). For end-to-end setup, see the Make your first call quickstart or the Google Ads MCP server guide . Go to Google Ads API Overview in Cloud Console Access levels There are four different API access levels listed in order in the table. If you don t already have Google Ads API access, you can start by enabling the API to obtain Test access level for your Google Cloud project, and then apply for Explorer access on the Google Ads API Overview page to access production accounts. Test access After you ve enabled Google Ads API, your Google Cloud project is granted Test access. This means that the project can only make Google Ads API requests against test accounts. Important: Refer to the test account guide to learn more about how to create a test account. Apply for Test access Enable Google Ads API in your Google Cloud project to automatically be granted Test access for your project. Explorer access level After you ve completed the initial sign-up for the Google Ads API, Google may let you apply for Explorer access level. The Explorer access level allows your Google Cloud project to make Google Ads API requests against both test accounts and production accounts. Production accounts are any accounts that serve real, live Google ads test accounts don t serve ads. The Explorer access level allows your Google Cloud project to execute up to 2,880 operations per day against production accounts. This is sufficient for most developers to get started with the API and build basic automation. The Explorer access level restricts access to the following features. If you need to use these features, you need to apply for Basic access level or Standard access level . Basic access level The Basic access level allows your Google Cloud project to make Google Ads API requests against both test accounts and production accounts. The Basic access level allows your Google Cloud project to execute up to 15,000 operations per day. This is sufficient for most developers. Navigate to the Google Ads API Overview page in your Google Cloud project. Verify that the page displays your current access level as Explorer . Click to expand the Upgrade access level section. Confirm that the Next access level is displayed as Basic . Confirm that there are no warnings indicating that you haven t completed brand verification for your project. If there are, follow the instructions to complete brand verification before continuing. Click the Apply for access button to apply for Basic access level. Google may automatically upgrade your project s API access level to Basic once you submit your application. Standard access level Standard access level allows your Google Cloud project to execute an unlimited number of operations per day for all services. Individual services and features may still have rate limits and restrictions that are specific to those features, which will continue to apply even if your project has Standard access level. The Standard access level is only granted to developers who require unlimited Google Ads API operations, such as large companies or tools that serve many users. Apply for Standard access level Navigate to the Google Ads API Overview page in your Google Cloud project. Verify that the page displays your current access level as Basic . Click to expand the Upgrade access level section. Confirm that the Next access level is displayed as Standard . Click the Start application button to start the Standard access level application. The Standard access application involves a detailed manual audit of your application. Be prepared to answer questions about your tool s functionality and its target audience. If your tool is used by external users, be prepared to provide demo sign-in access to your tool. Note that your tool must comply with the Required Minimum Functionality . Throughout the review process, the Google Compliance team will communicate with you using your email address. Make sure you respond promptly to the queries from the Compliance team to make progress with your Standard access application. When the review is complete, Google will email you with the final outcome of the review process. API quotas and system rate limits Regardless of the access level, all API operations are subject to system rate limits, which restricts how many operations you may perform in a period of time, that is the number of operations per hour. To learn more about how to handle rate limit errors, see error types . Individual services may enforce additional limits and quota restrictions due to reasons such as product design limitations, product policy restrictions, API performance and latency considerations. See the documentation about API quotas to learn more about these restrictions. Permissible use Permissible use only applies to Google Cloud projects with Standard access level. Permissible use is allocated based on intended use of the Google Ads API. These permissions determine which features of the API your tool can use, as elaborated in the following table: Permissible Use Description Ad creation / management Provide access to all services of the API for creating and managing Google Ads campaigns, ad groups, ads, and keywords. Reporting Only make GoogleAdsService.Search or GoogleAdsService.SearchStream requests, or read-only calls. This is for developers who only use the API to request stats. Researching keywords and recommendations Allow the Google Cloud project to access RecommendationService , KeywordPlanIdeaService , and KeywordPlanService . This is only used by tools requiring suggestions to help facilitate the creation and management of Google Ads campaigns. Change permissible use If your Google Cloud project has been approved for Standard access level, you can fill out the application to update permissible use . Fill out the application if you would like to update your permissible use or grant your clients access to your tool. Page Summary outlined_flag User authentication for accessing the Google Ads API involves using an OAuth 2.0 flow. The OAuth 2.0 process issues an access token that allows the app to make API calls to the user s account. Requesting OAuth 2.0 offline access is common practice to refresh authorization without user interaction. User authentication can be implemented for single user scenarios or multi-user scenarios. This guide explains how to access the Google Ads API using user authentication. See the overview guide to learn more about the available authentication options. The user authentication workflow uses an OAuth 2.0 flow to obtain human authorization, allowing your app to manage Google Ads accounts on behalf of users. After the user completes authorization, the authorization server issues an OAuth 2.0 access token. Your app uses this access token to make API calls to the user s Google Ads account. Because OAuth 2.0 access tokens expire after one hour, request OAuth 2.0 offline access . Offline access provides a refresh token that lets your app automatically generate new access tokens without requiring repeated user interaction. To generate an OAuth 2.0 refresh token using the user authentication workflow, the authorizing user must authenticate with a passkey . Choose an authentication strategy You can implement the user authentication workflow in one of two ways: Single-user authentication: Recommended when a single user account has access to all the Google Ads accounts your app needs to manage. Use single-user authentication as an alternative to the service account workflow when organizational policies or account configurations prevent you from using service accounts. Multi-user authentication: Recommended when your app manages accounts owned by multiple distinct users. This approach requires you to build an OAuth 2.0 flow that lets each user authenticate individually.
