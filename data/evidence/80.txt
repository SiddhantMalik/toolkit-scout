You can still view the legacy API V1 documentation . Help Topics Authentication Introduction The V2 API requires an access token to authenticate requests. There are two options available to you: A Personal Access Token which is tied directly to you and is the quickest way to start playing around with the API. Implementing a full OAuth2 Authentication flow which allows other people to use your Harvest integrations. Personal access tokens The API can be accessed by creating a Personal Access Token from the Developers section of Harvest ID. After creating it you’ll be provided with a random token and a list of your account IDs. Personal Access Tokens are the preferred method when you want to write your own scripts that consume our API. Typical use cases for Personal Access Tokens are scripts that build custom reports, sync data between different accounts, or automate tasks that would otherwise take a long time when done manually. Personal Access Tokens replace the Basic Authentication method that was used in our v1 API, as this is more secure. Within the Developers section you’ll see a list of all your Personal Access Tokens, when they were last used, and you’ll be able to easily revoke them if necessary. Once generated, a Personal Access Token can be used to access the API by either providing the token in the Authorization header or including it in the query string. Each request will require your account ID as well, since you can use this Personal Access Token to access any of your Harvest or Forecast accounts. Header authentication example curl -H "Authorization: Bearer $ACCESS_TOKEN " \ -H "Harvest-Account-Id: $ACCOUNT_ID " \ -H "User-Agent: MyApp ( [email protected] )" \ https://api.harvestapp.com/v2/users/me Query string authentication example curl -H "User-Agent: MyApp ( [email protected] )" \ "https://api.harvestapp.com/v2/users/me?access_token= $ACCESS_TOKEN account_id= $ACCOUNT_ID " OAuth2 application If you are interested in building integrations that other users can use, you will need to register an OAuth2 Application, also known as an OAuth2 Client. The application can be created from the Developers section of Harvest ID, and you will be required to provide some information: Name –name of your application. Redirect URL –the URL in your integration; successful authentications will be redirected to by default. Multi Account –does your integration support multiple user account access or work with only one authenticated account. Products –scope of access requested; can be either Harvest, Forecast or both. It is advised to pick the minimal scope required for the integration to work. OAuth2 authorization flow For server-side applications We use the Authorization Code flow for server-side authorization. To start the authorization flow, you need to redirect the user to the following URL: https://id.getharvest.com/oauth2/authorize?client_id={CLIENT_ID} response_type=code This URL allows the user to authenticate on Harvest ID and lets them authorize access to their account(s) depending on your OAuth2 Application settings and their choice. This endpoint accepts other parameters: state –(optional) used to pass any value that will get sent back to you when redirecting back to your application. redirect_uri –(optional) the default Redirect URL can be further customized here if needed, but needs to start with the Redirect URL registered with your Application. After a successful authorization, the user will be redirected back to the Redirect URL you specified when registering your OAuth2 application, or the redirect_uri you provided. These parameters will be attached: code –an authorization code that you will have to exchange for a set of Refresh and Access Tokens. You will be able to use this Access Token to access the user’s account on their behalf. state –(optional) contains the original value for the state parameter that was passed at the beginning of the authorization. scope –contains a list of space-separated strings describing the granted access scope. See the Scopes section for further explanation. Once you have the Authorization Code, you can exchange it for a set of Access and Refresh Tokens: curl -X POST \ -H "User-Agent: MyApp ( [email protected] )" \ -d "code= $AUTHORIZATION_CODE " \ -d "client_id= $CLIENT_ID " \ -d "client_secret= $CLIENT_SECRET " \ -d "grant_type=authorization_code" \ 'https://id.getharvest.com/api/v2/oauth2/token' Response: { "access_token" : "{ACCESS_TOKEN}" , "refresh_token" : "{REFRESH_TOKEN}" , "token_type" : "bearer" , "expires_in" : 1209600 } When your Access Token is about to expire, you can use the Refresh Token to get a new Access Token: curl -X POST \ -H "User-Agent: MyApp ( [email protected] )" \ -H "Accept: application/json" \ -d "refresh_token= $REFRESH_TOKEN " \ -d "client_id= $CLIENT_ID " \ -d "client_secret= $CLIENT_SECRET " \ -d "grant_type=refresh_token" \ 'https://id.getharvest.com/api/v2/oauth2/token' Response: { "access_token" : "{NEW_ACCESS_TOKEN}" , "refresh_token" : "{REFRESH_TOKEN}" , "token_type" : "bearer" , "expires_in" : 1209600 } For client-side applications We use the Implicit Grant flow for client-side authorization. These are typically applications that run entirely on the browser and issue Cross-Origin requests to our API. The difference is that you’ll get a single Access Token back that you can use immediately. If a backend server is available, we recommend the Authorization Code flow , because it’s more secure and the access token is never visible by a browser. To start the authorization flow, redirect the user to the following URL: https://id.getharvest.com/oauth2/authorize?client_id={CLIENT_ID} response_type=token This URL allows the user to authenticate on Harvest ID and lets them authorize access to their account(s) depending on your OAuth2 Application settings and their choice. This endpoint accepts other parameters: state –(optional) used to pass any value that will get sent back to you when redirecting back to your application. redirect_uri –(optional) the default Redirect URL can be further customized here if needed, but needs to start with the Redirect URL registered with your Application. After a successful authorization, the user will be redirected back to the Redirect URL you specified when registering your OAuth2 application, or the redirect_uri you provided. These parameters will be attached: access_token –the Access Token token that can be used to authenticate the requests on the user’s behalf. token_type –will always be bearer . expires_in –time in seconds until the token expires. state –(optional) contains the original value for the state parameter that was passed at the beginning of the authorization. scope –contains a list of space-separated strings describing the granted access scope. See the Scopes section for further explanation. Scopes and account access Personal Access Tokens have the all scope by default, so you have full access to all of your accounts. For OAuth2 Applications, it can vary depending on the options you selected and the authorization the user might give you. The scope can contain one or more of these values: harvest:{ACCOUNT_ID} –a Harvest account ID that the user granted access to. forecast:{ACCOUNT_ID} –a Forecast account ID that the user granted access to. harvest:all –the user granted access to all of their Harvest accounts. forecast:all –the user granted access to all of their Forecast accounts. all –the user granted access to all of their accounts. If you registered your app as needing access to just one account, the user will choose which account to authorize, and you’ll only get one scope back, either harvest:{ACCOUNT_ID} or forecast:{ACCOUNT_ID} , depending on which products you chose to work with. If your app can work with multiple accounts, you can get any combination of those scopes depending on what the user chose to authorize. Use that list or consume Harvest ID’s accounts endpoint to figure out which accounts you can access: GET https://id.getharvest.com/api/v2/accounts Example Request (note that the account ID is not necessary): curl "https://id.getharvest.com/api/v2/accounts" \ -H "Authorization: Bearer $ACCESS_TOKEN " \ -H "User-Agent: MyApp ( [email protected] )" Example Response: { "user" : { "id" : 1 , "first_name" : "Albert" , "last_name" : "Llop" , "email" : " [email protected] " }, "accounts" : [ { "id" : 10254 , "name" : "Sterling Cooper Advertising Agency" , "product" : "harvest" }, { "id" : 88888 , "name" : "Iridesco" , "product" : "forecast" }, { "id" : 88903 , "name" : "Sterling Cooper Advertising Agency" , "product" : "forecast" } ] } Still have questions? Help Topics Planned Expenses A planned expense is committed future spend on a project row of the Forecast board — a purchase order, a subcontractor, a licence — which the board adds to that project’s forecast cost, and to its forecast revenue when it is re-billed to the client; it is the plan, not money already spent, so there is nothing to reconcile with a Harvest expense. This page covers listing the plan, reading one row back, and creating, editing and deleting one. The planned expense object Attribute Type Description id integer Unique ID for the planned expense. project_id integer The board project the spend is committed against. It is set on create and never changes: the amount is denominated in that project’s currency, so a move would silently re-label a committed figure. description string What the spend is for, up to 255 characters. amount decimal The committed amount, in currency , with at most two decimal places. It must be greater than 0 and less than 1,000,000,000 . currency string The three-letter ISO 4217 code the amount is denominated in. It is stamped from the project’s currency — the project’s own code, then its client’s, then the account’s — when the expense is created, and it never changes afterwards, so editing the project’s currency later never re-labels a committed amount. There is no conversion between currencies. expected_on date The day the spend is expected. billable boolean true when the expense is re-billed to the client, so it also counts towards the project’s forecast revenue. Defaults to false . expense_category object The account expense category the expense is filed under, or null when it is uncategorised. See the expense category object . A row keeps the category it was filed under even after that category is archived. updated_at datetime Date and time the expense was last updated. Use the ISO 8601 Format . The expense category object Attribute Type Description id integer Unique ID for the expense category. name string Name of the expense category. is_active boolean false once the category has been archived in Harvest, which is how /v2/expense_categories reports the same state. An archived category stays on the rows already filed under it. Required permissions Both halves of this surface are behind the same two account switches, checked in this order, and both refusals are the account’s rather than the caller’s: the account must be in the Forecast financials rollout, or every request answers 403 with Forecast financials are not enabled for this account ; the account’s Project financial estimates switch must be on, or every request answers 403 with Project financial estimates are turned off for this account . On top of those, the caller must be allowed to see cost rates, or the request answers 403 with Not authorized! — a planned expense is cost data, and the cost-rate permission is an ordinary one, so its refusal keeps the generic wording. On the list, the two switches are the first gates a request meets. On the write half the shared Forecast account and caller gates described below answer before them, so the order a caller sees the refusals in depends on which half it calls. The two caller-side gates are worded differently on the read and on the write, because the two halves do not share a controller: the list is served by the collection endpoint, which answers one message for a caller with no Forecast seat, no board scope, or a company whose permissions regime is not ready: 403 with Forecast access is required for this endpoint . It is asked of the same predicate the board asks, so a caller who can open the board can list the plan. the member read and the three writes inherit the Forecast base controller, so the account gate and the caller gate are the shared Forecast ones: 403 with Forecast is not enabled for this account when the account has no Forecast board or is not on the permissions framework the caller’s scopes are written in, and 403 with Forecast is not enabled for this user when the caller has no Forecast seat or no claim that grants a board scope. Creating, editing and deleting additionally need a Forecast write claim and an account that is not read-only: a caller who can read the plan but not write it answers 403 with Forecast editing access is required . Retrieving one expense is the dependent read of a write, so it does not need it — a read-only seat reads back the row it can list. A write is then bounded per project, by the caller’s edit scope. A caller scoped to the whole plan may write an expense on any project; a caller scoped to the projects they manage may write only expenses on those projects, and naming another project answers 403 with Not authorized! . A caller scoped to their own schedule has no planned expenses at all: their list is empty and every row answers 404 with Record not found . The shared Forecast gates, the beta contract, pagination and the error envelope are on the Forecast API overview . The amounts listed here are the cost side of the project financials . List planned expenses Beta endpoint. Fully available, but the response shape may still change. Until it is frozen, every response includes Harvest-Api-Stability: beta . Returns the committed spend on every project the caller’s board shows, ordered by expected_on and then by id . The read is not windowed: it is the whole plan, not a date range. There is no project or date filter. A project_id , client_id , from , to or scope sent in the query string is ignored rather than honoured — the scope is resolved from the token’s user, never from a request parameter. A row on a project that has been archived, or that is not on the board, is absent from the list. The response contains an object with a planned_expenses property that contains an array of up to per_page planned expense objects, plus the pagination properties and the two completeness fields. truncated reports whether the board’s own project list was cut at 2,500 projects, which is the only cap that can omit rows from this list; truncation.projects carries that cap when it was reached and null otherwise. The cap is reported on every page, so following next_page to the end does not clear it — and pagination counts the rows within the cap, so total_entries describes the listed subset, not the plan a truncated board holds. A page past the last one answers an empty array with the plan’s total_entries rather than an error. GET /v2/forecast/planned_expenses Parameter Type Description page integer The page number to use in pagination. (Default: 1) It must be an integer greater than 0, and no larger than 2305843009213693 ; a larger one is refused with 422 rather than answered with an empty page. per_page integer The number of records to return per page. Can range between 1 and 2000. (Default: 2000) cursor string Accepted and ignored: this collection is paged by offset only. A malformed value is still refused with 422 by the shared cursor validator. updated_since datetime Not supported: an archived project removes its rows without stamping them, so a delta would silently miss exactly those rows. Any value is refused with 422 ; an empty one is treated as absent. Fully available, but the response shape may still change. Until it is frozen, every response includes Harvest-Api-Stability: beta . Commits a planned expense to a project and returns it with a 201 Created response code and a Location header holding the URL of the new expense. The body answered is the same field set show serves, so the Location reads back the row that was created. The body is read as a JSON object, and only the fields below are writable. currency_code is not one of them: the currency is stamped from the project on create, and a client that sends one is ignored rather than re-denominating a committed amount. company_id and updated_by_id are server-set and ignored if sent. The project is the record’s gate as well as its owner. project_id must name a project the caller may write: a project outside the caller’s edit scope answers 403 with Not authorized! , and a project that is not the account’s own — an unknown id, or another company’s project — is refused by the model with 422 and Project can't be blank or Project must belong to the same company . A project that is simply archived or not yet on the board is not refused: the row is a real row and stays readable through show . A create is not idempotent: two identical requests commit two expenses. A write does not touch the project it belongs to — no project updated_at moves, no notification or email is sent, and no Activity Log entry is written.
