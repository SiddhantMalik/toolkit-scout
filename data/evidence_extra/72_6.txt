Third-party integrations via OAuth overview - Help article that discusses the broader ways to manage which third-party integrations have access to your Airtable data. What are personal access tokens? Personal access tokens (PATs) allow users to create multiple access tokens that allow for a wide range of access to the information held in Airtable bases. For example, on the narrow end, you can create a PAT that only has a single scope to a single base in Airtable. On the deep end, however, you could have a "main/overarching" token that has access to all workspaces and bases with all available scopes included. Further, admins can adopt user role access on workspaces and bases in their enterprise for which they are not direct collaborators. PATs allow admins access to workspaces and bases added to their organization. The admin who owns the PAT does not need to be a direct collaborator on every workspace and base within the organization. Instead, the PAT adopts the user role permissions for those bases and workspaces. Accessing personal access tokens Open the developer hub . Click Personal access tokens under the “Developers” section. Creating personal access tokens Open the developer hub . Click Create token . Name your token. Click + Add a scope . Check out developer documentation to learn more about scopes. Click + Add all resources / + Add a base to select your token’s access level. Options include choosing a single base, multiple bases—including bases from different workspaces—all current and future bases in a workspace you have access to, or even all of the bases in every workspace you have access to, including bases and workspaces added in the future. What the token can do in each base still depends on your permission level there. In the resource picker you can search for a base or workspace by its ID as well as by its name. This is useful when several bases share a similar name, or when you already have the base ID from a URL or an API response. Updating personal access tokens Open the developer hub . Scroll or search for the name of the PAT that you want to update/edit. Click the token's name. Alternatively, click the … icon to the far side of the PAT, then click Edit token . Update the name, scopes, or access for the PAT. Click Save changes . Regenerating or deleting personal access tokens Open the developer hub . Scroll or search for the name of the PAT that you want to regenerate or delete. Click the … icon to the far side of the PAT. Click Regenerate token or Delete token . Regenerating a token will cause a warning message to appear. Remember that any services currently using this token will need to be updated with the new token that is generated. Limiting a token to a specific set of bases You can't scope a personal access token to a managed app or to any other custom group of bases. Tokens can be scoped to individual bases, to workspaces, to all of your workspaces, or, for enterprise admins, to an entire organization. To give a token access to a specific set of bases—including bases added later—keep those bases in a dedicated workspace and add that workspace to the token. Create a workspace for the bases the token needs to reach. Move the bases into that workspace, or create them there. Add the account that will own the token to the workspace. For integrations, this is usually a service account. Open the developer hub while signed in as that account, and create a new token or open an existing one. Click + Add a base , then select the workspace. The token checks which workspace a base is in each time it's used. Bases created in or moved into the workspace later are covered automatically, and a base moved out of the workspace loses access right away. You don't need to own the workspace to add it to a token, but the token can only do what your permission level allows in each base—for example, Editor to update records and Creator to change fields and tables. If your organization's admin has turned on "Block API access to organization-owned bases and workspaces," the account must also be on the API access allowlist. FAQs What can my personal access tokens access? Unlike legacy API keys, which have the same access as your Airtable account, you can limit and configure the access of your personal access tokens. You can do this by selecting the scopes (what endpoints the token can use) and access/resources (which bases and workspaces the token can access) when creating or updating a token. Regardless of the scopes and access a user selects for their token, the token will only be able to perform actions that the user creating it is allowed to do. For example, to create a new field in a base via the API, the user must be a Creator collaborator in the base and the token must have the schema.bases:write scope and the base added as a resource. For more information about how scopes and access work, see the Authentication developer reference . For more information about configuring your token's access, refer to the personal access tokens guide . How do I find my API key? Typically, this error type indicates either: A permissions-related issue, in which case you’ll want to: Check your PAT scopes Check your permissions level in the base you are referencing See if field and table permissions might also be causing the invalid permissions error. An issue with the base referenced, in which case you’ll want to: Double-check that the base id referenced is correct Confirm that the base has not been deleted More common API troubleshooting information is available here . I’m not able to access the enterprise scopes. What might be occurring? The ability to add enterprise. scopes is restricted to Enterprise Scale plans. This feature is not available on Business plans. Upgrading to an Enterprise Scale plan is required to use this functionality. Do personal access tokens expire? By default, no. A personal access token has no expiration window of its own and stays active until it is deleted, regenerated, or modified. One exception applies: on enterprise organizations, an admin can set a policy that caps the maximum lifetime of a personal access token. When a token passes that cap, requests using it fail with UNAUTHORIZED - Invalid authentication token . If you're on an enterprise organization and a token that previously worked stops being accepted, ask your admin whether a token lifetime policy is in effect. If no lifetime policy applies and a PAT stops working, the cause is one of the following rather than expiration: The token was regenerated, which invalidates the previous token value, so any service still using the old string will fail until updated with the new one. The token was deleted, or its scopes or base/workspace access were changed. If a PAT failure is happening in the environment or application consuming the token, check there, and with that platform's support, if Airtable shows the token as active. You can review your tokens any time in the developer hub under Personal access tokens. I have checked my scopes and IDs and still get an INVALID_PERMISSIONS_OR_MODEL_NOT_FOUND error. What else could cause it? If your scopes, workspace/base IDs, and access all check out and you're on an enterprise organization, the most likely cause is an org-level API restriction set in the admin panel, not your token. When an admin enables "Block API access to organization-owned bases and workspaces" (under Settings → Integrations & development), only users on the API access allowlist can use personal access tokens against organization-owned resources — and requests from anyone not on the allowlist return INVALID_PERMISSIONS_OR_MODEL_NOT_FOUND , even with fully correct scopes and IDs. To resolve it, ask one of your internal Airtable admins to add you (or your service account) to the allowlist for that setting. If the admin needs guidance, point them to Settings – Airtable admin panel. The other documented causes remain worth ruling out: field/table editing permissions and an incorrect or inaccessible base/workspace ID. Can I use a personal access token to write to a synced table? No. You can't create or delete records in a synced table, or edit its synced fields, with a personal access token, whatever scopes the token has. A synced table takes its values from its source, so Airtable returns an error such as Your record could not be created because the underlying table is externally synced. This also applies indirectly: a write to a linked record field fails if it would need to create a new record in a synced table. You can still write to fields you've added to the synced table yourself. Automations can't write to one-way synced tables; with two-way sync, automation actions (but not scripts) can make the edits the sync allows. Can I limit a personal access token to a single interface? No, you cannot scope a personal access token to an interface or to an individual view. Token access is granted per base and per workspace, so a token can reach any table or interface in a base it has access to, within the limits of its scopes. If your team works only in interfaces and you need to narrow what a token can reach in the underlying data, use Airtable field and table editing permissions on the tables and fields themselves. Those permissions are honored by API requests, just as they are in the Airtable UI. Why does my personal access token return "UNAUTHORIZED - Invalid authentication token"? This error means Airtable did not accept the credential sent in your request's Authorization header. It returns HTTP status 401 with this body: {"error":{"type":"UNAUTHORIZED","message":"Invalid authentication token"}} It is a different error from AUTHENTICATION_REQUIRED , which means no credential reached Airtable at all, and from INVALID_PERMISSIONS_OR_MODEL_NOT_FOUND , which means the token was accepted but doesn't have the scopes or resource access the request needs. A token that is rejected here never got as far as a scope or base check, so re-checking scopes and base access won't resolve it. Work through these causes in order: Only the token ID was sent. A complete token is a 17-character ID, a period, then a 64-character secret. The secret is displayed only once, at creation. If you no longer have it, regenerate the token and copy the whole value. The secret was truncated or altered between copying and sending. Check for missing characters, added whitespace, or a line break introduced by the tool storing the token. The token was deleted, regenerated, or had its access modified after you copied it. Confirm it still appears in the developer hub. The token has passed a maximum lifetime set by an admin. On enterprise organizations, an admin policy can cap how long a personal access token stays valid. Once a token is past that cap, every request using it returns this error even though the token still looks correct and still appears in your token list. Ask one of your Airtable admins whether a token lifetime policy applies to your organization. The endpoint doesn't accept personal access tokens. A small number of endpoints accept only other credential types, and a personal access token sent to one returns this error regardless of its scopes. To narrow down which of these applies, repeat the request with response headers shown — for example, curl -i instead of curl -s : If the response includes a WWW-Authenticate header containing error="invalid_token" , Airtable recognized the value as a personal access token and rejected it during validation. The cause is one of the token-specific items above. If that header is absent, the value wasn't recognized as a personal access token at all. Look for a malformed or truncated credential, or an endpoint that doesn't accept personal access tokens. For error codes beyond authentication, see Airtable API: Common troubleshooting . Never paste a complete token into a support ticket, community post, or chat conversation. Redact everything after the period, and regenerate any token whose secret you've shared.
