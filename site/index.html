1 · The patterns (headline)

  1. Getting a developer key is rarely the problem; production is. 76 of 95 apps hand a developer free or trial credentials, but 25 of those 76 add a second gate before you can use the API on other customers' accounts (app review, partner approval, KYC, a paid plan). Only 11 gate even the first credential (sales contact, customer-only, partner or enterprise licence) and 7 need a paid plan.
  2. OAuth2 and API keys are the two auth patterns, and most apps offer both. OAuth2 appears in 75/95 apps, API key or bearer token in 72/95, Basic in 12, JWT in 5. Only 13 are key-only, so a toolkit can usually offer a zero-friction key path plus an OAuth path.
  3. An official MCP is now the norm, not a differentiator. 80/95 apps ship a vendor MCP (70 remote, 10 local). My memory-only first pass missed it for 39 of the 100 apps. Caveats: the second audit counted roughly 8 of the official MCPs as beta, early access or preview (for example Stripe, Podio, BigCommerce, WooCommerce), and some cover only part of the product (Plaid's covers Dashboard diagnostics). "Has an official MCP" does not mean "toolkit is done". Docs-only MCPs (Mailchimp, Magento, Shopify's dev MCP) are not counted.
  4. The most common blockers are not paywalls. Admin-only credentials, production approval, app review, and per-tenant or per-region hosts outnumber paid-plan gates several times over (chart below). Note these flags (admin-only, tenancy, narrow API) are agent judgements that were not required to carry a quote, so they are the least verified numbers on the page. They are cheap to handle in a toolkit design (document the admin step, collect the subdomain or region at connect time) but they stop a "paste a key and go" flow.
  5. Easy wins cluster in productivity and data/SEO apps; friction clusters in fintech, ecommerce and support. Developer platforms sit in the middle. Easy: Productivity 8/10, Data/SEO 7/10. Lowest: Fintech 0/8, Ecommerce 2/10, Support 2/9.
  6. Outreach list (needs a partnership or sales contact): DealCloud, Pylon, Gladly, Aircall, LinkedIn Ads, Pinterest, Salesforce Commerce Cloud, Amazon Selling Partner, Waterfall.io, Binance, Brex, Ramp, PitchBook. Not buildable as an API toolkit: Sherlock, Mermaid CLI. Needs a human to decide what the app even is: Cloudflare, Paygent Connect, Otter AI, YouTube Transcript.

3 · The agent and where a human was needed

0 · Baseline memoryPass 1 written from model memory before I opened any docs (git timestamps can't prove that, so treat it as stated, not proven).
1 · Retrieve scriptfetch_evidence.py: docs + llms.txt + one hop to auth/pricing/MCP pages; flags JS shells. mcp_probe.py: MCP registry leads.
2 · Extract LLM agents10 parallel extractor agents, one prompt and schema. Every field needs a verbatim quote + URL, else unknown.
3 · Verify scriptcheck_quotes.py checks each quote appears in the saved page text; gate.py resets fields whose quotes all fail.
4 · Verdict codeverdict.py derives easy/caveat/hard/no/unknown from the fields, so the label is reproducible.
5 · Score scriptscore.py against gold sets frozen in git before scoring (hashes below).

What ran where, plainly

  • Stage 2 ran as Claude subagents inside a Claude session (40 apps on Sonnet, 60 on Opus). Seven of the ten first-launch Sonnet runs died on API overload (HTTP 529) and were re-run; six moved to Opus. The per-range log is data/run_log.json; it was written by the orchestrator, because the tooling kept no model tags. I did not use Composio's SDK or MCP to build this; stages 1, 3, 4 and 5 are plain Python and the stage-2 prompt is in agent/prompts/extract.md so it can be driven by any model or swapped onto Composio tools.
  • The sandbox shell could reach many doc sites but not all. 13 apps have at least one quote that came through a web-fetch tool rather than a saved page, so the checker could not verify it (31 quotes). Sites that blocked scripts or needed JavaScript include Salesforce, Otter, PitchBook, Binance, Lark, Airtable, Gumroad, Consensus and the Amazon and Google docs.
  • Human involvement: none yet. No person reviewed these rows. 79 apps carry an open question for a human (entity decisions, pricing that isn't public, login-walled docs, rubric judgement calls). The 7 that most need a person: Paygent Connect and YouTube Transcript (entity ambiguous); fanbasis, Coda and NotebookLM (renamed); Otter and PitchBook (docs unreadable to the agent). Four rows were corrected by me after the second audit (Pinterest MCP, Magento auth, iPayX access, Ramp auth); they are logged in data/pass2/corrections.json and none is in a gold set.

4 · Verification: how accurate is it, honestly

Read this first. Both gold sets were labelled by Opus agents from primary docs, not by humans. Gold A (27 apps, an independent reviewer) was picked to be suspicious and obscure, so it exaggerates pass-1 error. Gold B (20 apps, seeded random, 2 per category, labelled blind before any pass-2 output existed) is the fair estimate, but n=20 means 95% intervals of roughly ±20 points. Extractors were told not to open any gold or review file, but that blindness is by instruction, not enforced by the sandbox, and I (the orchestrator) had read the reviewer's findings, which contain the gold A answers, before launching them. Treat gold A's pass-2 numbers as not blind. Gold B was frozen before pass-2 scoring, but its labeller is also a Claude model, as are the extractors and the auditor, so shared blind spots are possible.

What moved accuracy, and what didn't

  • Memory → evidence-grounded extraction did the work. Official-MCP detection went from 16/20 (80%, CI 58–92) to 20/20 (100%, CI 84–100) on the random sample and from 8/24 (33%, CI 18–53) to 22/24 (92%, CI 74–98) on the hard cases. Most of the gain is freshness (2025–26 vendor MCP launches, renames), which a memory-only baseline can't know. That baseline is deliberately weak.
  • The quote gate barely mattered for accuracy. It checked 575 quotes: 540 found in the page text the extractor saved for that app (it does not check that the text came from the cited URL, and some saved files are 404 pages or AI-assistant answers), 31 unverifiable, 4 failed; it reset one field (Cloudflare access) and changed no gold-scored result. It is there for auditability, and it found a bug in itself (it dropped non-Latin characters until an extractor's Japanese quotes failed).
  • Verdict got worse than memory on both gold sets, under the rubric as first written (v1). Exact agreement: gold B 65% (pass 1) vs 55% (pass 2), gold A 71% vs 59%. Every disagreement is within one step on easy/caveat/hard. The second audit found holes in my rubric: an official MCP excused gated developer access, a paid plan needed only for production never counted as friction, and unknown fields defaulted to "easy". I fixed these after seeing gold (v3, used for the per-app labels and patterns on this page). v3 scores 65% on gold B (the gain comes from two apps, Amazon SP-API and PitchBook) and 53% on gold A, so it is a post-hoc variant, not a clean improvement. Do not read the verdict column as validated.
  • Auth got worse on gold A by exact match (88% → 53%). Extractors list every supported method while gold lists the reviewer's primary one, so an extractor that adds OAuth to an API-key app fails exact match. Exact-set match is the strict metric; Jaccard (shown next to it) is the softer one. Neither is a clean measure because gold A's auth labels are incomplete.
  • Pass 1 vs pass 2 changed 40 MCP calls, 21 access classes, 35 auth sets and 47 verdicts across all 100 apps. Only the gold-sampled ones have a ground truth to say which side was right.

With n=30 each agreement rate has a 95% interval about 15–20 points wide, so a 97% reads as "somewhere from about 83% to 99%". The weak spot is evidence quality, not the facts: in 13 of 30 apps at least one cited quote only partly supports its value or contradicts it (Pinterest, Magento and iPayX were outright wrong and are corrected above). In the 40-entry integrity check, 39 of 40 quotes were still on the cited page, but only 26 clearly supported the field they were attached to; 6 supported it only weakly or trivially (a package slug, an aggregator page the prompt forbids), 3 partly, and 5 not at all (for example a 10DLC registration sentence cited for a free trial). The auditor is the same model family as the extractors, so "agrees" is not human-grade truth. Full audit: audit/audit.md, row-level: audit/crosscheck.jsonl.

Other things the agents got wrong or could not settle

  • Entity resolution: "Paygent Connect" matches no single product; "YouTube Transcript" resolved to a third-party service (TranscriptAPI), not Google's captions API; fanbasis is now Commas; Coda is now Superhuman Docs; NotebookLM's API is the enterprise "Gemini Notebook Enterprise". All five are flagged, not guessed.
  • Some extractor labels are provisional: Threads' MCP type is an inference from a docs index whose pages came back empty; WhatsApp's "admin-only credential" has no quote behind it; Shopify's store-management MCP is announced but not live (recorded as docs-only); WooCommerce's MCP is a per-site developer preview.
  • Pricing tables rendered as icons or JS could not be read for Copper, Devin and Pylon, so "which plan unlocks the API" is unconfirmed there.

6 · Run it

git clone <repo> && cd toolkit-scout
python agent/fetch_evidence.py          # stage 1: fetch docs, save page text
python agent/mcp_probe.py               # stage 1b: MCP registry leads
# stage 2: run agent/prompts/extract.md per app with any LLM -> data/pass2/raw_*.jsonl (included)
python agent/gate.py                    # stage 3: quote check + gate
python agent/score.py pass2b=data/pass2/pass2b.jsonl pass2b_v2=data/pass2/pass2b.jsonl
python agent/analyze.py && python agent/build_site.py   # regenerates every number on this page
